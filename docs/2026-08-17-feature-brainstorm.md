# dsh-lark 新功能脑暴清单

> 日期：2026-08-17
> 基于版本：dsh-lark-channel 0.0.6
> 定位约束：本插件是 DSH 的 IM 遥控器（Feishu/Lark channel），不是通用飞书 bot。
> 评估维度：**用户价值**（是否高频痛点）× **实现成本** × **与 channel 定位契合度**。

## 现状摘要

当前已具备的能力域（详见 README 与各模块文档注释）：

1. **聊天 ↔ Agent 桥接**：每聊天独立 agent、持久会话、`sessionScope` 三种粒度、`/new` epoch 重开、`/cd` 多工作区、`/model` 切换、`/status` 状态查询
2. **输出渲染**：原生 CoT 思考过程消息（默认）/ stream 打字机卡片、`attachImages` 图片入站
3. **人机协作卡片**：提问（shadow `ask_user_question`）、计划审阅（shadow `exit_plan_mode`）、工具审批、防注入双语卡片体系
4. **命令体系**：`/stop` `/help` + host 命令直通、飞书斜杠面板 reconciling 同步
5. **权限与多 Agent**：allowlist/approvers 收窄模型、多实例 add/remove、bot 互聊（botHops 预算）
6. **部署运维**：一键 CLI（systemd/launchd 后台服务）、二维码首启注册、credentials 引用存储、WebSocket liveness 看门狗

---

## P0 — 直接补齐核心体验闭环

| # | 功能 | 理由 |
|---|---|---|
| 1 | **文件收发**：入站文件（日志/文档/代码）落入工作区供 agent 读取；agent 产物（报告、diff、生成的图表）作为文件消息回传 | 当前最大的能力缺口。开发者场景里"发日志给它排查"和"把报告拿回来"都是刚需，目前入站只支持图片（且默认关），出站只有纯文本。README 的卖点是"不用守着终端"，但产物拿不回来就还得回终端 |
| 2 | **长任务进度心跳 + 完成时 @ 发起人** | 核心卖点是"派任务后离开"，但长任务的静默期用户完全无感知，完成消息也不 @ 人，在活跃群里会被淹没。加"仍在运行（已 N 分钟，正在执行 X）"的低频心跳和完成时 @，闭环"派活—离开—被叫回"体验。可顺带在运行中卡片上放"停止"按钮，移动端免打字 |
| 3 | **上下文水位预警**：接近上限时主动提示（附 `/compact` `/new` 按钮） | `/status` 已经拿到了上下文占用数据，增量成本极低；而用户不会主动查水位，撞墙时体验是"突然变笨或报错"。低成本高感知 |
| 4 | **图片失败自动降级**：路由拒收图片时自动剥离图片重试，并提示"当前模型不支持视觉" | README 明确写明这是深坑——一张截图会因为历史重发永久毁掉会话且无法从聊天恢复。目前的解法是把责任推给部署者手工配 `attachImages`，自动降级能把"毁灭性故障"变成"一条提示" |

## P1 — 显著增强，成本可控

| # | 功能 | 理由 |
|---|---|---|
| 5 | **会话管理 `/sessions`**：列出本会话的历史 epoch/目录会话，支持切回 | epoch 机制刻意保留旧 session 在盘上（"聊天命令不该能销毁记录"），但只进不出——`/new` 之后没有任何入口找回上一个会话。存量机制已备好，缺的只是入口 |
| 6 | **自定义快捷指令（prompt 模板）**：如 `/review <PR>`、`/daily` 展开为预设 prompt，按实例/群配置 | 团队工作流沉淀的载体。同一个群反复输入同样的长指令是真实摩擦；有了它，多 bot 协作（reviewer bot）也能一键触发标准动作 |
| 7 | **审批体验增强**：卡片超时未处理时提醒 approver；同会话"记住此工具的批准"（会话内 always-allow） | `approvers` 机制已完整，缺的是运营体验：审批人漏看卡片会让任务无限挂起；重复批准同一工具造成审批疲劳，疲劳的结果是无脑点允许——反而更不安全 |
| 8 | **机器人自定义菜单同步**：把 `/status` `/new` `/model` 等挂到飞书 bot 原生菜单 | 与 slash-panel 同构的 reconciling 思路可直接复用；移动端点菜单远比打命令顺手，而移动端恰是"不守终端"场景的主战场 |
| 9 | **`/usage` 成本统计**：按会话/按天汇总 token 消耗与估算成本 | `/status` 已有单会话累计 token，聚合展示是自然延伸；多人共用 bot 的部署（群场景）尤其需要成本可见性 |

## P2 — 有价值但依赖外部条件或场景较窄

| # | 功能 | 理由 |
|---|---|---|
| 10 | **定时任务**：`/cron "每天 10 点检查 CI"`，定时唤起 agent 并推送结果 | 价值高（晨检、日报是飞书原生习惯），但需要新增调度层与持久化，且"无人值守跑任务"放大了审批与安全面，适合在 P0/P1 稳定后做 |
| 11 | **产物写入飞书文档**：长报告写成飞书云文档回链接 | IM 里读长报告体验差，文档是正确归宿；但扫码创建的应用需要额外申请文档 API 权限，改变了"扫码即用"的零配置故事，需要设计成可选能力 |
| 12 | **Reaction 轻交互**：用表情回应确认收到/轻量批准；bot 用 reaction 表示"处理中" | 飞书原生玩法、降噪（少发一条消息），但属于锦上添花 |
| 13 | **审计日志导出**：谁在何时批准了什么工具调用，集中可查 | 卡片已记录决策人，但分散在消息流里；对合规敏感的团队有价值，个人用户无感 |
| 14 | **配置热重载** | README 明确"改配置需重启"是已知摩擦，但涉及运行中会话与连接的迁移语义，成本高收益中 |
| 15 | **语音消息转文字输入** | 移动端场景加分项，依赖语音识别能力，需求频度存疑 |
| 16 | **Windows 服务支持** | 目前 Windows 降级前台运行；补齐部署矩阵，但目标人群（跑 DSH 的开发者）多在 macOS/Linux |

## 明确不建议做

- 群聊内容总结、知识库问答一类"通用飞书 bot"功能——偏离"DSH 的 IM 遥控器"定位，DSH 生态里应由其他插件承担。

## 推荐起步

第一个开发的功能建议选 **#1 文件收发**：它是能力性缺口（其他多为体验性），且入站（文件落工作区）和出站（产物回传）可拆成两个独立的小迭代。
